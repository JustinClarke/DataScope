# ADR-004: Monaco integration approach

**Status:** Accepted — 2026-07-19. Decided from this phase's own Monaco integration build, per D18 (spike-first process).

**Referenced by:** `build/04-sql/01-monaco-editor.md`

## Context
Resolves the Monaco integration approach — raw `monaco-editor` vs. `@monaco-editor/react` — including which import path keeps the lazy-loaded chunk small, self-hosted worker wiring (matching ADR-001's same-origin posture rather than Monaco's CDN-loader default), and how the DuckDB-aware completion provider is wired in. Deferred until this phase's editor work produced real integration evidence (bundle cost, completion-wiring ergonomics), per the spike-first process.

## Decision
**Raw `monaco-editor`** (pinned exact, `0.55.1`), imported with the bare `import * as monaco from 'monaco-editor'` entry point — not a hand-narrowed import graph, and not `@monaco-editor/react`. The editor is created directly with `monaco.editor.create()` inside a component that only ever loads behind `React.lazy()` (`src/features/sql/MonacoWrapper.tsx`), mounted from `SqlModule.tsx`'s `<Suspense>` boundary.

Key fit points, in order of how they were actually established:

1. **A hand-narrowed import graph bought nothing, so the simpler bare import won.** The natural instinct — import only `edcore.main.js` (core editor + built-in contributions, no language services) plus `basic-languages/sql/sql.contribution.js` (just the SQL Monarch tokenizer), skipping the ~70 other basic-language tokenizers and the TypeScript/JSON/CSS/HTML language services pulled in by the default `monaco-editor` entry point — was built and measured against the bare import. Both produced the same shipped chunk: **925.38 KB gzip (narrow) vs. 927.04 KB gzip (bare)**, a difference inside build-to-build noise. The reason: Monaco's own basic-language contribution files are already behind *internal* dynamic `import()` calls, so a bundler (Vite/Rollup here) splits each of them into its own small chunk regardless of which entry point pulls the package in — confirmed in the production build output, where `sql-*.js` (8.84 KB), `mysql-*.js`, `pgsql-*.js`, etc. all ship as separate chunks alongside the core `editor.api2-*.js` chunk, never inlined into it. Hand-narrowing the import graph only added three import lines and a risk of silently missing something the full editor needs, for zero measured byte savings — so the bare import was kept.
2. **`@monaco-editor/react` adds a dependency and a CDN-avoidance step, with no bundle-cost or missing-manual-work upside.** Swapping the same feature onto `@monaco-editor/react@4.7.0` (still backed by the same local `monaco-editor` package, via `loader.config({ monaco })` to avoid its default jsdelivr-CDN fetch — CDN loading would break the same-origin/CSP posture ADR-001 already established for DuckDB's assets) produced an identical core editor chunk (926.82 KB gzip — the same package, so no reason to expect otherwise) plus a **larger wrapper chunk**: 110.70 KB / 27.49 KB gzip for `@monaco-editor/react`'s own component + its `@monaco-editor/loader` dependency, versus 53.68 KB / 14.43 KB gzip for the hand-written wrapper doing the same job directly. It also still required the exact same manual self-hosted-worker setup (`self.MonacoEnvironment.getWorker` pointed at a same-origin `?worker` import) that raw usage needs — the wrapper does not remove that step, since worker hosting is a `monaco-editor` concern, not a React-binding one.
3. **The manual lifecycle work the wrapper library would have saved was already small and already needed.** Direct `monaco.editor.create()` plus a single `useEffect` cleanup (`dispose()` on the editor, its `onDidChangeModelContent` subscription, and its keybinding action) is ~30 lines and already correctly guards against the leaks a naive integration would hit on remount. `React.lazy()` + `<Suspense>` already provides the "don't load until needed, show a fallback while loading" behavior a wrapper library's own internal loading-state management would otherwise offer — adopting `@monaco-editor/react` for that would have meant two overlapping "is it loaded yet" mechanisms (React's own `Suspense` boundary and the loader's internal promise-based state) rather than one.
4. **Store-driven completion source needs the same wiring either way.** `monaco.languages.registerCompletionItemProvider('sql', ...)` reads `useDatasetsStore.getState().tables` fresh on every trigger (not a value captured at mount time), so a table added, dropped, or derived mid-session shows up on the very next completion — this registration is identical code whether the editor instance underneath came from raw `monaco.editor.create()` or from `@monaco-editor/react`'s `onMount` callback, since both hand back the same `monaco` namespace and editor instance. No ergonomic difference here favored the wrapper.

## Alternatives considered
- **`@monaco-editor/react`.** Rejected — see point 2 above: same core bundle cost, additional wrapper-chunk weight (~13 KB gzip more), an extra dependency, and a CDN-avoidance configuration step to keep it consistent with this app's same-origin asset convention, for no reduction in the manual worker-hosting or completion-wiring work.
- **Hand-narrowed `monaco-editor` import graph** (`edcore.main.js` + `basic-languages/sql/sql.contribution.js` only, skipping the default entry point's other languages and language services). Rejected — see point 1: measured to save nothing (Monaco already internally code-splits its per-language contributions), so the added import-path complexity and the risk of a narrow path missing something the full editor needs weren't worth carrying.
- **CDN-hosted Monaco assets** (either raw `monaco-editor`'s documented CDN pattern or `@monaco-editor/react`'s loader default). Not adopted, for the same reason ADR-001 bundles DuckDB's assets same-origin: a CDN `.wasm`/script fetch is the kind of cross-origin subresource `COEP: require-corp` is positioned to block, and this app's established convention is same-origin, content-hashed, long-lived-cached assets.

## Consequences
- `monaco-editor` is pinned exact (`0.55.1`), matching this project's convention for WASM/bundle-size-relevant dependencies (`@duckdb/duckdb-wasm`, `apache-arrow` — both also pinned exact) rather than the caret-range convention smaller UI dependencies like `fflate` use; a bare `latest` install is not assumed safe for a package this size and this load-bearing for the §22-class lazy-load gate.
- The Monaco chunk is large in absolute terms — **3.6 MB raw / ~925 KB gzip** for the core editor chunk alone (measured from the production build, `editor.api2-*.js`), plus a same-origin `editor.worker` chunk (~280 KB raw), the codicon icon font (~122 KB), and Monaco's own CSS (~146 KB raw / ~23 KB gzip). This is materially larger than the master doc's own "~2 MB" description of the Monaco bundle — worth a documentation correction pass, not made here since this ADR's authorized scope is the integration decision and its own spike evidence, not a general edit to that doc's bundle-size table. The architecture this ADR commits to (lazy-load, self-hosted, no CDN) is unaffected by the estimate being off; only the descriptive number elsewhere is stale.
- Because the chunk is large regardless of import-path choice, the lazy-load boundary (`React.lazy()` triggered only once the SQL sidebar card is clicked) is the entire mitigation — there is no smaller-bundle escape hatch available within `monaco-editor` itself for a SQL-only editor. Confirmed empirically: the app's initial entry chunk is unaffected (85.57 KB gzip after this build vs. 84.31 KB gzip before — the ~1.3 KB gzip delta is this feature's own non-Monaco code, not Monaco itself), and a production-build network capture showed zero Monaco-chunk requests before the SQL card's first click, with both Monaco chunks (`MonacoWrapper-*.js`, `editor.api2-*.js`) firing immediately after.
- The self-hosted worker (`monaco-editor/esm/vs/editor/editor.worker?worker`, same-origin, matching ADR-001's Worker-loading convention) is the only worker registered — no TypeScript/JSON/CSS/HTML language-service workers, since none of those language contributions are used by a SQL-only editor.
- `registerCompletionItemProvider` is a global, package-level registration (not per-editor-instance) — guarded by a module-level flag so remounting the lazy-loaded wrapper (e.g. leaving and re-entering the SQL tab) never double-registers it and never offers each suggestion twice.

## Spike evidence
No separate throwaway harness — the evidence is this phase's own build, measured directly against the production `vite build` output:
- **Narrow vs. bare `monaco-editor` import:** 925.38 KB gzip vs. 927.04 KB gzip for the core editor chunk — noise-level difference, both far above the "hand-narrowing helps" assumption; per-language chunks (`sql-*.js` 8.84 KB / 3.73 KB gzip, `mysql-*.js`, `pgsql-*.js`, `tsMode-*.js`, etc.) appear as separate chunks under both import paths.
- **Raw `monaco-editor` vs. `@monaco-editor/react`:** identical core editor chunk cost (927.04 KB vs. 926.82 KB gzip, i.e. the same package); wrapper-chunk cost 53.68 KB / 14.43 KB gzip (raw, hand-written) vs. 110.70 KB / 27.49 KB gzip (`@monaco-editor/react` + `@monaco-editor/loader`).
- **Entry-chunk impact of this feature:** 84.31 KB gzip → 85.57 KB gzip (before/after), confirming Monaco itself never reaches the entry chunk — only this feature's own small non-Monaco module code does.
- **Live verification (production build, `vite preview`, headless Chromium via a disposable Playwright harness — not committed to the repo):** zero Monaco-chunk requests captured on initial page load; both `MonacoWrapper-*.js` and `editor.api2-*.js` requests fire only after the SQL sidebar card's first click. Autocomplete against a real ingested sample (`ecommerce`) returned real table and column names (e.g. `orders`, `order_items`, `order_id`, `order_date`) via the completion provider reading the live table registry. A real query against a loaded table returned results with a measured execution time (4–5 ms on the sample data), reflected in the results pane, the status console, and query history. A deliberately invalid query (`SELECT * FROM nonexistent_table_xyz`) surfaced DuckDB's own catalog error ("Table with name nonexistent_table_xyz does not exist! Did you mean \"order_items\"?") in the results pane, readable and non-crashing.
- **Unverified — do not read broader coverage into this ADR:** only headless Chromium was exercised (no Firefox/Safari); no measurement of Monaco's cold-start/compile time in isolation (only the DuckDB engine's cold-start was measured in ADR-001); no large-document editor performance test (all queries typed in this evidence were short, single-statement SQL).
