## Spike findings log

Record Phase-1 ingestion-spike and D17 inference-spike findings here (and mirror durable
design consequences into the master doc — §21 plus the §23.1 CSP note for the ingestion
spike; §20.6 for the D17 spike) before writing the ADRs:

- *Ingestion spike (2026-07-19 — **GO**, ADR-001 / master §21):* COOP/COEP confirmed but
  not load-bearing — with the headers `crossOriginIsolated` is true and DuckDB-Wasm auto-selects
  its threaded `coi` bundle; **without them it does not fail and does not drop to the baseline
  `mvp` — it selects `eh` (single-threaded, WASM exception handling), fully functional** for
  both ingest and query, so the single-threaded fallback *suffices* where headers can't be set
  (just slower on heavy ops). Cold-start (production build, headers on): **799 ms cold / 631 ms
  warm** for `coi`, every measured path under the <3 s target; dev single-threaded `eh` init
  (517 ms) is *faster* than dev threaded (1314 ms) — threading is a query-time, not startup, win.
  Timings were compile-bound over localhost, so a real deploy adds the ~7.8 MB-gzip threaded-bundle
  download atop the ~0.6–0.8 s compile floor. Threading payoff is scoped to heavy ops on large
  files: on a 50.7 MB / 1.24 M-row CSV, threaded ingest 1.8× (240 vs 426 ms) and SUMMARIZE 3.1×
  (262 vs 800 ms) faster; sub-1 MB within noise. Memory: that file materialized to **~87 MB
  DuckDB engine memory** (~1.7× on-disk, via `duckdb_memory()`). **Negative finding — main-thread
  `performance.memory` is useless here** (flat, quantized 11.9 MB before/after: DuckDB's data lives
  in the worker WASM heap and Chrome quantizes the API against fingerprinting), so §15 memory
  budgets must use `duckdb_memory()` or `performance.measureUserAgentSpecificMemory()`, never bare
  `performance.memory`. Build carry-overs: bundle DuckDB assets **same-origin** (Vite `?url`) +
  ordinary same-origin `Worker` (not `blob:`, so `worker-src` needs only `'self'` and COEP doesn't
  block a CDN `.wasm`); lazy-init on ingestion intent behind a module-level singleton promise
  (guards React StrictMode's dev double-invoke, observed spawning two workers); immutable HTTP
  caching over a hand-rolled Cache API (the ~21% warm gain was V8's code cache); threading as
  enhancement (detect `crossOriginIsolated`, degrade, never hard-gate); **pin an explicit stable
  `@duckdb/duckdb-wasm` (1.32.0), not `latest`** (which resolves to a dev prerelease). Unverified:
  Chromium-only (Safari COOP/COEP/SharedArrayBuffer quirks want a pre-launch check, no Firefox run),
  localhost-only timings (no CDN/throttle), Parquet path implemented but unmeasured, no OOM / >50 MB
  probe. Disposable harness + full verdict in the spike scratchpad.
- *07a persistence spike (2026-07-29 — **GO on (B)**, ADR-011 / master §5.2 Revised(18)):*
  the workspace can survive a refresh, but **not** by opening DuckDB against OPFS. Machine
  **Apple M1, 8 GB** (the S0 reference machine; **the M4 Air arm was not run**), Chromium 151
  headless + **real Safari 18.6** (a self-reporting probe page, since Playwright cannot drive
  Safari and WebKit-via-Playwright is not the browser the claim is about),
  `@duckdb/duckdb-wasm` 1.32.0, `eh` bundle. **The pre-committed kill criterion did not fire:**
  a second tab's open fails fast and legibly on both engines (~3.2 s — `Access Handles cannot
  be created…` / `The object is in an invalid state.`), never hangs, and never corrupted or
  deadlocked the first tab (500,000 rows intact on reload after every contention trial; on
  Safari the first tab kept read *and* write). **Candidate (A) is rejected on a finding nobody
  had listed:** a database closed with an **empty WAL reopens read-only** — reads complete and
  correct, every write refused with `Failed to commit: File is not opened in write mode`, and a
  further reload does not clear it (read-only 5/5 in the isolating trial and 2/2 at 500k rows
  before it; read-write 13/13 when the WAL was non-empty at close). That is the
  restored-workspace case itself. **Second (A)-only finding, recorded for anyone who revisits
  it:** writes are durable only after an explicit `CHECKPOINT` — 8/8 trials kept committed rows
  with one, 8/8 lost them without, even after a graceful `terminate()`. **(B) is cheap and
  portable:** staging 17.2 MB = 79 ms (Chromium) / 101 ms (Safari), re-register + `CREATE TABLE
  AS` 132/439 ms; at 43 MB, 148 ms + 401 ms — **sub-second, cheaper than the re-drop it
  replaces**. Build carry-overs: **staging writes go through a worker sync access handle**
  (Safari 18.6 has no `createWritable` on an OPFS handle at all); **capability detection belongs
  in the worker** — the main-thread `createSyncAccessHandle` check reports *false* on both
  engines while the worker call succeeds, so detecting on the main thread would disable
  persistence everywhere; and **"Clear workspace data" must terminate the engine before emptying
  OPFS**, since `removeEntry` on a held file fails with `NoModificationAllowedError` (the naive
  order silently half-clears). Quota is not a constraint at the §7.3 tiers (10.74 GB Chromium /
  82.46 GB Safari against a 300 MB ceiling), but `persist()` is **denied** on both, so OPFS is
  evictable and 07d's *Lost* outcome is ordinary. Unverified: the M4 Air, headful Chrome's
  `persist()` heuristics, Firefox, real eviction under quota pressure. Disposable harness
  (`spike-07a/`) deleted; full verdict in ADR-011.
