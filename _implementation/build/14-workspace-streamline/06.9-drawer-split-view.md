# S6.5 — The drawer split view

**Tier:** v0.70 (the workspace streamline, D73 execution) · **Master spec:** §13.3 (the bottom
region — the permanent split, its geometry, the detail-ladder table's rung 2, pane mechanics,
viewer mode), §10 Module 2 (the console's contents), §15 (Monaco's lazy boundary) · **Decision
row:** D73 (no row is reversed at the decision level; §13.3's own charter is scoped further —
see scope call 1) · **Depends on:** v0.70 S3/S4/S5 (all shipped) · **Gated by S0:** no.

**This doc was rewritten on 2026-07-29, mid-build, against a human redesign** (recorded in the
`BUILD-ORDER.md` entry of that date). The first version specified a console-left split with Info
as a clamped-width sidebar and the console keeping its results. What shipped inverts both. The
scope calls below describe **what was built**; where the first version said something else, the
change is named rather than quietly replaced, because a leaf doc that reads as if it always said
this is worse than one that shows its own reversal.

## Objective

Replace S3's tab switch (Info ⇄ Console) with a **permanent split, one job per pane**:

- **Info, on the left** — the selection scent as a capped top strip, then everything a run
  produced: the results grid, its chart, the exports, Pin-to-tab, the export recipe, the history.
- **The SQL editor, on the right** — code and nothing else, plus Run and Format.

Expanding does not only make the drawer taller: it **turns the split on its side**, editor above
and Info beneath as the results panel. A drawer too narrow to sit the panes abreast stacks them
the same way. **Neither pane is ever hidden at any width**, which is what removes the view
switcher rather than merely making it inert.

The split is the visible half. The half that answers the reported pain is the **division of
labour**: today a user scrolls past a suggestions block, then past a 256px editor, to reach the
result they just produced. Splitting the code from its consequences is what makes that scroll
distance zero — a horizontal split alone would have delivered the same stack in a narrower column.

## Scope calls

**1. Info holds the output; the SQL pane holds only code. Its scent strip keeps the charter.**
Human call, 2026-07-29. §13.3 held the bottom inspector as "scent, not dashboard," and D73 had
already reversed that *at the region level* to admit a results grid while keeping "no charts in
the inspector" true of Info. This carries the same reversal to its end: the chart moves in beside
the result. The charter is **scoped one level further — to Info's scent strip**, where it still
holds in full, and the strip stays rung 2 of the detail ladder with its click-through intact. The
alternative considered and rejected was dropping the scent entirely; it would have deleted rung 2
and left D24's edge add/remove/repoint controls with no home.
*What the SQL pane no longer holds:* `QueryOutput`, `QueryHistory`, Pin-to-tab, the export
recipe. All four are Info's now.

**2. Info is on the left, the editor on the right.** Human call, 2026-07-29, reversing the first
version's console-left resolution (and §13.3's record of it, amended in the same pass). Info sits
under the explorer rail whose selections feed it, and the editor takes the reading-end position
where the caret spends its time. The shell's spatial grammar (explorer left, canvas centre, AI
pane right) is unaffected — the drawer sits beneath all of it.

**3. One clamped ratio, not a fixed sidebar.** Also reversing the first version, which argued a
ratio "adds a second layout axis." That argument held while Info was one line of scent text; it
does not once Info holds a results grid, because then both panes need real width. `infoRatio`
defaults to an even share, clamps to `[0.3, 0.7]`, and is dragged from the divider. The clamp is
the whole guarantee that neither pane reaches zero — **a run landing in an invisible pane is how
a user confirms a transform through the guard modal and then never sees what it did.** The same
ratio drives both layouts, because it means the same thing in each (Info's share of the drawer),
so expanding changes the axis and not the proportion the user chose.

**4. `expanded` stacks the panes, and fixes a shipped defect.** Human call, 2026-07-29 for the
stacking; the fix was already this leaf's. The shipped S3 implementation set
`height: expanded ? '100svh' : height` on a `shrink-0` element whose in-flow siblings are
`WebLLMDock` and the status bar, with no `overflow-hidden` on the outer column — so expanding
**pushed the dock and the status bar below the fold, taking the privacy posture dot with them.**
That violated §13.3's "expands against the canvas, never over the dock" and S3's own checked
acceptance criterion (`03-item-inspector-drawer.md:265–266`), which had been checked against an
assertion its test never made. `expanded` is now `calc(100svh - CHROME_RESERVE)` — the same
reserve drag-to-max already used, so the two gestures agree — and the stacking gives the result
the drawer's full width, which is what the gesture was asking for.

**5. There is no view switcher, and `view` is deleted.** The first version kept `view` and the
`ViewButton`s inert above a 900px threshold and live below it, falling back to S3's tabs on a
narrow drawer. That fallback is replaced by **stacking**, which is strictly better — both panes
stay visible — and it leaves `view`, `showView` and `DrawerView` with no consumer at all, so they
are removed rather than kept as residue. The collapsed drawer's way back in is the chevron, whose
`aria-label` names what re-opens it.

**6. What `openInfo()` and `activateConsole()` become.** Master §13.3's "any selection opens the
drawer if collapsed and selects Info" stands. With both panes always visible there is no view to
switch, so a selection made while the drawer is open produces **no chrome movement at all** — on
a pane the user may not be looking at. So `openInfo()` keeps `open: true` and bumps an
`infoSignal`, which Info watches to (a) **reset its scent strip's scroll to 0**, since a previous
selection's offset would render the new content below the fold, and (b) **mark its header
briefly** in the HUD's active register. No layout shift, no motion, no toast, **no focus steal** —
the caret is usually in the editor next door. `activateConsole()` (S4's six remote run surfaces)
bumps a `consoleSignal` that scrolls Info's output region back to the top, so a run started
elsewhere shows its own answer without a further gesture.

**7. The re-open cost is recorded at its new weight.** `openInfo()` un-collapses on *every*
selection change, and collapse is the only way to get the drawer out of the way. A user reading
the ERD who clicks three nodes re-opens the drawer three times — S3 scope call 8's accepted cost,
now heavier, because the drawer that returns contains a mounted Monaco. Master's behaviour is
followed rather than softened; the mitigations that do not contradict it: the collapse control's
`aria-label` and tooltip **say what will re-open it**, and a re-open restores the last
`height`/`infoRatio` rather than defaults.

**8. `QuerySuggestions` is not rendered in the console, and this leaf owns the removal.** S3 scope
call 4 deferred it ("S6 moves `QuerySuggestions` to the map"); S6's box is still unchecked. It was
the single largest contributor to the reported scroll distance, so it could not fall through the
gap a third time. Removed here; **S6 keeps only the map-side placement.** The component and its
test are left in the tree for S6 to re-home — deleting them would destroy the work S6 needs.

**9. Monaco loads whenever the drawer opens.** Closed human decision, 2026-07-28. S3 made the
boundary the console's *editor activation* (cold pane + "Open SQL editor" control +
`consoleActivated`). Under a permanent split the editor is visible whenever the drawer is, and a
cold pane occupying half of every open drawer is worse than the chunk. `consoleActivated` and the
cold pane are retired. **§15's hard requirement is unaffected — Monaco is still never in the
module graph at shell mount**, because the drawer's body does not mount until a drawer opens.
*Recorded consequence, not hidden:* the drawer's default is `open: true`, so in practice the chunk
is fetched when the workspace first renders rather than on a later gesture. That is the trade the
2026-07-28 decision made.

**10. Monaco gets a themed editor, and this — not the split — is the fix for the reported "white
flash."** `monaco.editor.create` was called with **no `theme`**, so the editor was permanently
Monaco's default `'vs'` light theme inside the HUD's dark register; nothing in `src/` called
`setTheme` or `defineTheme`. `monacoTheme.ts` now defines a theme from the **live computed
tokens** — resolved through `getComputedStyle` on the editor's own container, so a
register-pinned subtree wins — and passes it to `create`. Monaco's format takes only hex, and the
tokens are `oklch`, so the values are converted through a canvas 2D context, the one colour parser
in the platform that accepts both. **The file declares no colour literal of its own:** a fresh
context's default `fillStyle` is read as the "parse failed" baseline rather than named, and an
unresolvable token is *omitted* so Monaco's own base fills it — a slightly-off editor beats a
stale literal nobody notices has drifted. This is the opposite conclusion to V6b's
`lib/chartPalette.ts`, deliberately: that file carries resolved literals because its palette has
its own `design.md` section to be checked against, and the editor has no palette of its own.
The Suspense fallback also gained a surface token and the editor region's height.

**11. SQL indentation and a real formatter — human call, 2026-07-29.** Monaco's bundled SQL
contribution ships brackets and comments but **no `indentationRules`**, which is why `autoIndent`
looked inert on a SQL buffer: it had nothing to consult. Registered here, with
`autoIndent: 'full'`. Beyond that the human chose the formatter over the config-only option, so
**`sql-formatter` (15.8.2) is a new runtime dependency**, wired as a
`DocumentFormattingEditProvider` (⇧⌥F, `formatOnPaste`) and behind the toolbar's Format button.
Dialect is `duckdb`, matching the engine (ADR-004) — a Postgres-shaped formatter mangles DuckDB's
own syntax. `keywordCase: 'preserve'`: the buffer holds text a person typed, and rewriting their
casing on a formatting pass is a change they did not ask for. **The dependency is kept off the
startup path** — `SqlModule` is in the shell's eager graph, so its Format handler imports the
formatter *on the click*; measured, this moved 73 kB gzip out of the startup chunk (279 → 206 kB).
The provider registration rides `MonacoWrapper`'s existing lazy boundary.

**12. Viewer mode is inherited unchanged, and introduces no branch.** S3 scope call 11 restated:
`ViewerMode.tsx` renders its own `data-region="inspector"` and never mounts the drawer, so the
D62 consumption-only absence §13.3 requires is already structural. A permanent split makes
"Info only, no console" a *layout* claim as well as a mount claim, which invites exactly the
branch S3 refused — a `viewerMode` conditional rendering the split with an empty editor pane would
hand a `.dsps` recipient query access over a report carrying no rows. **The explicit negative: S6.5
introduces no `viewerMode` conditional inside the drawer**, only the assertions that keep it that
way.

**13. `ResultsGrid` and `DataTable` are untouched, and one pre-existing oddity is recorded rather
than fixed.** The first version's premise — "`ResultsGrid` has no horizontal scroll region of its
own" — was wrong: `DataTable` already carries `overflow-auto` and `minmax(120px, 1fr)` tracks, so a
wide result already scrolls. Info's output region is `overflow-auto` on both axes above it, which
is what this leaf adds. Noted in passing and **not** changed, because it belongs to every
`DataTable` consumer rather than to this phase: its virtualised rows are `absolute … w-full`
against a container whose width is the *visible* width, not the scroll width, so a row's own box
is narrower than the header's while the grid tracks still align the cells.

## Non-goals

- **No persisted split geometry.** `infoRatio` follows `height` and the explorer rail's width in
  resetting on reload. **S6.9 answers that for the whole shell at once**, not here.
- **No generic `<SplitView>` component.** Two panes, one divider, one call site. An abstraction
  with orientation props is a single-use abstraction.
- **No second ratio for the stacked layout.** One scalar means one thing in both axes.
- **No `ResizeObserver`-driven expand threshold.** S3 scope call 7's `PROMPT_ABOVE_ROWS = 12` is
  still the right answer and the new layout does not reopen it.

## Acceptance criteria

- [x] With the drawer open, **Info and the editor are both visible** — Info left, editor right,
      each taking its share of one clamped ratio
- [x] The ratio drag-resizes and clamps; **neither pane can be dragged away**, and nothing about
      the split is persisted across reload
- [x] **Info holds the selection scent, then the result, chart, exports, Pin, export recipe and
      history**; the scent strip is capped so it cannot crowd the output out
- [x] **The SQL pane holds the editor, Run and Format and nothing a run produced** — no results,
      chart, history, Pin or export recipe
- [x] The console renders **no `QuerySuggestions` block**
- [x] Info's output region **scrolls on both axes**, independently of the scent strip
- [x] With `expanded === true`, **the WebLLM dock and the status bar remain in the viewport** —
      the drawer expands against the canvas, never over the dock
- [x] Expanding **stacks the panes**, editor above and Info beneath, on the same ratio
- [x] Below `SPLIT_MIN_DRAWER_WIDTH` the panes **stack rather than hiding one**
- [x] Selecting a table/column/edge **does not steal focus**, resets Info's scent scroll, and
      marks Info's header
- [x] Selecting an item with the drawer collapsed still opens it (master behaviour unchanged);
      re-opening restores the last `height`/`infoRatio`, not defaults
- [x] A run from a canvas surface returns Info's output region to the top without further gestures
- [x] **Monaco is not in the module graph on shell mount**, and mounts when the drawer opens — no
      cold pane, no `consoleActivated` gate
- [x] `editor.create` is called with a **non-default `theme`** built from the resolved tokens, and
      `monacoTheme.ts` adds no entry to `conformance.test.ts`'s literal allowlist
- [x] Format **rewrites the buffer through the store and never runs it**; the formatter is absent
      from the startup chunk
- [x] Viewer mode renders **no split, no divider and no editor pane**, and the drawer contains
      **no `viewerMode` conditional**
- [x] Info click-through still reaches a tab from all three selection kinds — rung 2 never
      dead-ends
- [x] `tsc -b` clean over `src/`; full suite green; `oxlint` clean; `vite build` clean

**Not a criterion here, by design:** persisted split geometry (S6.9); a generic split-view
component or a second ratio; a `ResizeObserver`-driven expand threshold; a keyboard toggle for the
drawer (S3 scope call 12, still deferred); a full responsive pass (§13.3's deferred small-viewport
question — stacking is a fallback, not an answer to it); `QuerySuggestions`' map-side placement
(S6's); `DataTable`'s virtualised row width (scope call 13).

## Definition of done

The drawer shows both things at once and each has one job: a SQL pane that is a themed, indenting,
formattable editor and nothing else, and an Info pane that fills from the selection and then shows
what the query actually produced — result, chart, exports — with no scrolling to find the thing you
just ran. Expanding gives the result the whole drawer, stacked under the editor, **without taking
the privacy posture off the screen** — the defect S3 shipped against its own criterion. Narrow
drawers stack rather than hiding a pane, so no viewport is left unspecified and no run is ever
invisible. Monaco still costs nothing until a drawer opens, and the formatter costs nothing until
someone formats. Viewer mode still has no console at all, and still without a conditional.
