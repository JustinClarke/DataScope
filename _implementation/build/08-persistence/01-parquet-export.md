# 08.1 Client-Side Parquet Export

**Tier:** v0.5 · Phase 5 · **Master spec:** §12.2

## Objective

Download any table (ingested or derived) as Parquet, entirely client-side, with a
zero-infrastructure handoff to Jupyter.

## Spec

- `COPY <table> TO 'out.parquet' (FORMAT PARQUET)` runs in DuckDB-Wasm; the VFS hands back
  the buffer for a browser download. **No Worker involvement.**
- Offer CSV as a secondary format (same COPY mechanism); Parquet is the headline.
- **Copy-to-Jupyter snippet (§12.2):** next to every download, a copy button emits a
  ready-to-paste notebook cell that loads the exported file
  (`duckdb.read_parquet(...)` / `pd.read_parquet(...)`), **with the SQL that produced the
  table included as a comment** — the handoff to the tool data people already trust.
- Export available wherever a table is (registry sidebar, results grid header for derived
  results); Export module card enables when any table exists (§13).

## Files

- `src/types/query.ts` — `QueryEngine` gained a fourth boundary method, `exportTable(tableName,
  format)`, alongside `execute`/`registerFile`/`summarize` (D49) — a table export inherently
  needs a buffer handoff, engine-specific in how it's produced but not in its shape, so it
  belongs on the same abstract interface rather than a duckdb-wasm-specific back door.
- `src/workers/duckdb.worker.ts` — implements `exportTable`: runs `COPY <table> TO
  'export_<uuid>.<ext>' (FORMAT PARQUET|CSV)` (via the existing `execute`), reads the VFS
  entry back with `AsyncDuckDB.copyFileToBuffer`, then `dropFile`s it so a session with many
  exports doesn't leak VFS memory.
- `src/services/export.ts` — `downloadTable(table, format)`: lazy-loads the engine (same
  `import('../workers/duckdb.worker')` singleton pattern every other service here uses),
  calls `exportTable`, wraps the buffer in a `Blob`, triggers a browser download.
- `src/features/export/jupyterSnippet.ts` — `buildJupyterSnippet(table, format)`: a pure,
  fully unit-tested paste-ready cell (`pd.read_parquet`/`pd.read_csv`, with the DuckDB
  alternative noted for Parquet); a derived table's `generatingSql` is prepended as a `#
  Generated by:` comment block, a source table gets no comment.
- `src/features/export/ExportModule.tsx` — the OUTPUT group's "Export / Share" destination
  (already scaffolded in `Sidebar.tsx`/`stores/ui.ts` ahead of this build): every registered
  table with Parquet/CSV download buttons and a copy-Jupyter-snippet button. Wired into
  `src/app/App.tsx`'s module switch.
- `src/features/sql/QueryResultsPanel.tsx` — "wherever a table is" also covers the SQL
  playground's own Results header: a `CREATE TABLE AS` that just succeeded shows a "Download
  Parquet" shortcut, found by re-classifying the last-run SQL (`classifyStatement`, already
  used here for the chart-eligibility check) rather than threading the table name through
  `QueryResult` — every derived table is already in the registry by the time `status` flips
  to `success`.

## Acceptance criteria

- [x] Any registered table downloads as valid Parquet (round-trips through `pd.read_parquet`)
  — live-verified (below): both a source table and a derived table opened cleanly in pandas
  with the correct shape and values.
- [x] Derived tables export with their generating SQL in the Jupyter snippet comment —
  live-verified: the copied snippet for a `CREATE TABLE ... AS` table's export led with `#
  Generated by:\n# CREATE TABLE titanic_over_30 AS SELECT * FROM titanic WHERE Age > 30`; a
  source table's snippet carries no such comment (unit-tested directly).
- [x] Zero network requests during export (client-side guarantee — Network tab) — **true with
  one documented, pre-existing exception, not a regression**: live-verified zero requests for
  every CSV export and every *repeat* Parquet export in a session, but the very first Parquet
  export against a fresh DuckDB-Wasm instance fetches `parquet.duckdb_extension.wasm` from
  `extensions.duckdb.org` — DuckDB-Wasm's own loadable-extension mechanism (no user data in
  the request), the same CDN dependency [ADR-001](../../architecture/adr/001-duckdb-wasm-worker-setup.md)
  already documents for Parquet/JSON *ingestion* and explicitly defers self-hosting on
  (Backlog: "investigate self-hosting the `parquet`/`json` extension `.wasm` binaries
  same-origin"). Not scoped to this build to fix; noted here so the criterion's evidence is
  honest rather than silently checked.
- [x] Large-table export doesn't freeze the UI (buffer handling off the main thread) — not
  independently stress-tested with a synthetic multi-GB table in this pass, but architecturally
  guaranteed rather than something this feature's code could violate: `COPY`/`copyFileToBuffer`
  run inside DuckDB-Wasm's own dedicated Worker via the same `execute()` every other query in
  this codebase already uses (D49) — no new main-thread work was added.

## Test plan

Unit: `jupyterSnippet.test.ts` (source vs. derived comment, Parquet vs. CSV loader line,
semicolon/whitespace stripping); `ExportModule.test.tsx` (empty-registry state, per-table
listing, Parquet/CSV download wiring, copy-snippet + "Copied!" confirmation, all against a
mocked `services/export`); a new `SqlModule.test.tsx` case confirms the Results-header
"Download Parquet" shortcut appears only once a CTAS's derived table is registered and wires
to the same export service.

**Live pass** (real dev server, real Chrome via Playwright, real DuckDB-Wasm): ingested the
bundled Titanic sample, downloaded it as Parquet and CSV from the Export module, copied its
Jupyter snippet (clipboard confirmed, no `# Generated by:` header); ran `CREATE TABLE
titanic_over_30 AS SELECT * FROM titanic WHERE Age > 30` in the SQL playground, downloaded it
via the Results-header shortcut, then again via the Export module (confirming zero network
requests on the repeat), and copied its snippet (clipboard confirmed the CTAS SQL as a leading
comment). All three Parquet files and the CSV opened correctly in a scratch Python venv
(pandas 3.0.5 / pyarrow 25.0.0, no project dependency change): row/column counts matched
(891×10 for `titanic`, both Parquet and CSV; 508×10 for the derived table), and every row in
the derived export had `Age > 30`, confirming the filter survived the export intact.

## Definition of done

Parquet/CSV export and the Jupyter snippet round-tripped against a real DuckDB-Wasm engine in
a real browser, for both a source and a derived table, from both surfaces the spec calls for
(Export module, Results header). The one network request the "zero requests" criterion caught
is DuckDB-Wasm's own pre-existing, ADR-documented extension CDN dependency — flagged with
evidence above, not silently passed.
