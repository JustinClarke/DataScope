# Opus adversarial review of DESIGN.md (exp20, grain rescue)

Reviewer: Opus, read-only on `RESEARCH.md`/`DESIGN.md`. Scope: DESIGN.md as drafted, checked
against the actual CSVs in `public/samples/`, the code it plans to reuse
(`src/lib/relationshipInference.ts`, `eval/chat/17-duckdb-local-chat/{ollama,score}.ts`), and
external platform facts (Ollama registry, Ollama context behaviour) verified live.

Verdict up front: the *shape* of the experiment is right — deterministic profile → generated
grain layer → ablation ladder → 3-bucket scoring is the correct instrument for this question.
But as written it cannot be run: one of the five datasets is not the dataset the design thinks
it is, the headline arm's mechanism cannot compute the headline measure, one arm is a duplicate
of another, and the trap category the whole experiment is named after carries only 7 of 34
gradable checks — too few to distinguish any plausible effect from noise. All four are fixable
without growing the runtime budget.

## BLOCKING

### B1. `weather.csv` is a single-city series. Six of its seven questions are degenerate.

**Issue.** §2 describes `weather.csv` as "3650 rows, multi-entity time series, grain =
city-day" and builds W1/W3/W4/W5/W6/W7 on multiple cities. Verified against the file: all 3650
data rows have `City = Springfield`, one row per date from 2015-01-01 to 2024-12-27. It is a
single-entity daily series — structurally identical to `stock_prices.csv`, which §2 introduces
as its *contrast*.

Consequences, question by question:

- W1 ("how many distinct cities") — answer is 1, a trivial `COUNT(DISTINCT)` with no content.
- W3 ("which city has the widest average swing") and W6 ("which city has the highest average
  humidity") — degenerate: any query that returns a city returns the right one, including
  `SELECT City FROM weather LIMIT 1`. A wrong-grain query scores **correct**.
- W4 ("average TempHighC per city") and W5 (the deliberate "legitimately-global" control) are
  **numerically identical**. The control that was supposed to prove "always group by city" isn't
  a free win now proves nothing, because grouping and not grouping give the same number.
- W7 ("for Springfield only, average WindKph") — the filter is a no-op; `WHERE City='Springfield'`
  and no WHERE clause return the same value. The F trap cannot fire.

**Failure scenario.** The run completes, weather scores near-ceiling on every arm including A0,
and the report reads "the method's gains are concentrated in ecommerce; weather shows no arm
effect." That is a data artifact presented as a finding. Worse, the §2 coverage check claims
multi-entity time-series coverage via "W3, W4, W6 vs the single-entity contrast in
stock_prices" — the experiment would ship claiming a trap family it never tested.

Second-order: this also silently deletes 2 of the 9 grain-tagged checks (W3, W4), leaving all
grain evidence in one schema. See B4/I1.

**Proposed fix (DESIGN.md §2, weather block — replace wholesale).** Re-cast `weather.csv` as the
**temporal-grain** dataset, which is what it actually is and which adds a trap family the bank
currently lacks entirely. Replace the weather table with:

| # | Category | Trap | Question |
|---|---|---|---|
| W1 | profiling | - | How many rows are in the dataset, and what date range does it cover? (2 checks) |
| W2 | profiling | - | Is there more than one location in this data? |
| W3 | analytical | TG | On average, how windy is the windiest day of a month? (per-(year,month) MAX(WindKph), then AVG — naive `AVG(WindKph)` is ~2x low and silently wrong) |
| W4 | analytical | TG | What is the average daily temperature swing (TempHighC − TempLowC) in each calendar month of the year? |
| W5 | analytical | - | What is the single global average TempHighC across all days? (floor / regression guard) |
| W6 | analytical | TG+F | Considering only days with Humidity above 70, what is the average monthly mean TempLowC? |
| W7 | analytical | F | What is the average WindKph in 2024? |

Add **TG** = temporal grain to the §2 trap legend. Update the §2 dataset caption to
"3650 rows, single-location daily series 2015-01-01 → 2024-12-27, grain = one row per day."

**Also add a build-order gate (new §7 bullet):** *"Before the question bank is frozen, a
`fixtures/dataset-facts.json` is generated by the harness (row count, column list, distinct
count of every Categorical column, min/max of every Temporal column) and every question's
premise is asserted against it. No question may name an entity dimension the data does not
have."* This is the cheap control that would have caught B1 at design time.

### B2. A2's generated views cannot compute the headline measure. Order value is `quantity * unit_price`, and FK inference has no basis for synthesising a product of two columns.

**Issue.** §3 specifies A2 as "for every confident child→parent edge, a rollup view aggregating
the child to parent grain." `relationshipInference.ts` yields the edge
`order_items.order_id → orders.order_id` and nothing more — it says *what joins to what*, never
*what the measure is*. A rollup of `order_items` to order grain, derived from the edge alone, can
only emit `COUNT(*)`, `SUM(quantity)`, `SUM(unit_price)`. **`SUM(unit_price)` is not order
value.** Order value is `SUM(quantity * unit_price)`, and no deterministic key-inference step
produces that expression.

Verified against the data: `order_items.unit_price` always equals the matching
`products.unit_price` (e.g. product 114 is 289.32 in `products.csv` and in every one of its
`order_items` rows), so `unit_price` really is a per-unit rate, not an extended amount.

**Failure scenario.** A2 emits `order_totals(order_id, line_count, total_quantity,
total_unit_price)`. The model, correctly following the directive to use the views, answers E3
"average order value" as `AVG(total_unit_price)` — a syntactically perfect, successfully
executing, **silently wrong** number that is off by roughly the average quantity (≈3x on this
data). A2 loses to A1 on exactly the questions the experiment exists to answer, and the
conclusion "auto-generated semantic layers do not transfer to small local models" is recorded
when the real finding is "our view generator emitted the wrong measure." This is the single
highest-cost defect in the document: it inverts the headline result.

**Proposed fix (DESIGN.md §3, A2 row + §7 "New" list).** Do *not* quietly hardcode
`quantity * unit_price`. Specify a deterministic, pre-registered measure-synthesis rule and
emit **both** candidates, which also converts this gap into the view-selection test §6 asks for
(see B5):

Replace A2's cell with:

> **A2 — + auto-generated grain-correct views.** For every confident child→parent edge,
> a rollup view aggregating the child to parent grain is emitted and offered as queryable.
> Measure synthesis is deterministic and pre-registered: (a) `COUNT(*)` as `<child>_count`;
> (b) `SUM(c)` for every Quantitative column `c`; (c) `SUM(a * b)` as `<a>_x_<b>` where, within
> the same table, `a` matches `/qty|quantity|units|count/i` and `b` matches
> `/price|amount|cost|rate|fee/i` and both are Quantitative — the extended-measure rule.
> Both `sum_unit_price` and `quantity_x_unit_price` appear in the view; the model must choose.
> Views are built from inference alone — the harness never hardcodes "order_items rolls up to
> orders", and never hardcodes which measure answers which question.

Add to §7 New: `synthesizeMeasures()` (the (a)/(b)/(c) rule above) and a committed
`fixtures/inferred-artifact.<dataset>.json` holding the exact edges, grain statements and view
DDL each dataset produces, regenerated and diffed as a build-order gate. Add to §5: *"The report
publishes the full inferred artifact per dataset, so a reader can judge for themselves how much
of the grain work the harness did versus the model."*

**Corollary to check at build time, not after:** on `ecommerce/`, `assembleEdges` will attach
`ambiguity` annotations to the surrogate-key edges — `order_items.product_id` (1–150) is fully
contained in `customers.customer_id` (1–400) with coverage 0.375, and `orders.customer_id`
(1–400) is fully contained in both `orders.order_id` and `order_items.order_item_id`. Name
agreement wins the ranking (`rankScore` +0.001), so the *edges* are right, but the near-tie is
under `AMBIGUITY_GAP = 0.05` and the ambiguity string will appear in A1/A2 context. Assert the
expected edge set in the fixture rather than discovering this in a scored run.

### B3. A5 is definitionally identical to A4. There is no ceiling arm.

**Issue.** §3's ladder is cumulative — each row says "adds over previous". A4 = A3 + plan-first,
and A3 = A2 + few-shot, and A2 = A1 + views. So A4 already *is* A1+A2+A3+A4. A5 is described as
"A1 + A2 + A3 + A4 together", which is the same prompt. A4's own mechanism cell even says
"...even when A2's views are also available", confirming the cumulative reading.

**Failure scenario.** One sixth of the entire compute budget (≈17% of ~4,000 model calls) is
spent re-running an identical configuration. A5 and A4 differ only by backend nondeterminism, and
the report shows a meaningless ±2pp "gain from stacking" that a reader will interpret as a real
effect. Separately, §4 defines the coder-vs-general pair as "A0 and A5 only", so the entire
coder arm rides on an arm that has no distinct definition.

**Proposed fix (DESIGN.md §3, restructure the table).** Make the ladder explicitly cumulative
and drop the duplicate, then spend the freed budget on the two arms that actually buy
attribution:

| Arm | Prompt contents | Mechanism under test |
|---|---|---|
| **A0** | Raw DDL + question | Floor |
| **A1** | A0 + deterministic profile + grain statements | Does showing structure help? |
| **A2** | A1 + generated rollup views | Marginal value of a generated grain fix, given the profile |
| **A3** | A2 + schema-derived few-shot | Marginal value of a worked example |
| **A4 (= full stack)** | A3 + forced plan-first structured output | Ceiling |
| **A2′ (ecommerce only)** | A0 + generated rollup views, **no profile** | Breaks the ladder's order-dependence: are the views load-bearing on their own? |
| **A1✗ (ecommerce only)** | A1 with the grain statement and fanout ratio **deliberately corrupted** (parent/child inverted, ratio negated) | Negative control: if accuracy does not drop versus A1, the model is not reading the profile and A1's gain is a token-count artifact, not a comprehension effect |

Add a sentence under the table: *"The ladder is cumulative, so each row's delta is that
mechanism's marginal contribution **given the preceding ones** — the report must not phrase any
result as 'X does not help', only 'X does not help given A1..A(n−1)'. A2′ exists so the headline
mechanism has one order-independent measurement."*

A1✗ is the cheapest falsifiability instrument in this whole review and should not be cut.

### B4. Statistical power. 7 grain-tagged checks and N=5 repeats at temperature 0 cannot detect any plausible effect.

**Issue.** Three compounding problems in §2/§4/§5:

1. **The trap sample is 7, not 35.** After B1 removes W3/W4, every grain-tagged check is
   E2, E3, E4, E6, E7, E8, E9 — seven, all from one schema. The 95% CI half-width on a
   proportion at n=7 is about ±35pp. Going from 1/7 to 5/7 correct — a spectacular effect — is
   p ≈ 0.13 by an exact paired test. Nothing the experiment could observe on the grain traps
   would be statistically distinguishable from noise.
2. **N=5 repeats at temperature 0 buys almost nothing.** Greedy decoding on a fixed prompt with
   a fixed digest is near-deterministic; repeats measure backend nondeterminism, not sampling
   variance. The design treats 5 repeats as if they were 5 independent trials. They are not, and
   the effective n for any confidence interval remains the number of *checks*.
3. **No pre-registered decision rule.** §1 states a hypothesis ("4B + method ≥ 14B baseline")
   with no effect size, no test, and no falsification condition. Whatever numbers come out, some
   narrative fits them.

**Failure scenario.** The run costs 15–25 wall-clock hours (34 checks × 6 arms × 5 repeats ×
4 models ≈ 4,000 calls, against exp17's measured 7–10h for a much smaller matrix), produces
A2 − A1 = +14pp on 7 grain checks (i.e. one extra check), and the report claims "the generated
grain layer rescues small models." A reviewer computes the CI, finds it spans zero, and the whole
experiment is unusable. Or the reverse: a real +2-check effect is dismissed as noise. Either way
the compute is spent and the question is unanswered.

**Proposed fix — three edits, net budget-neutral.**

*(a) §2, question bank.* Raise grain-tagged checks to **≥20 across ≥3 schemas**. The additions
in I1 (chasm-join dataset) plus B1's temporal-grain weather questions plus the view-selection
questions in B5 get there without new data authoring.

*(b) §4, controls — replace the N=5 line.*

> - Repeats: run a **determinism probe first** — 20 identical calls, one prompt, one model,
>   temperature 0 — and record the identical-output rate in the manifest. If ≥95%, run **N=2**
>   (one repeat as a determinism audit, not a statistical sample) and spend the saved budget on
>   question count. If <95%, the backend is not deterministic and N=5 is justified; report the
>   probe result either way. Repeats are never treated as independent trials in any confidence
>   interval — the unit of analysis is the *check*.

*(c) §5, scoring — add an "Analysis plan (pre-registered)" subsection.*

> - Primary endpoint: correct-rate on **grain-tagged checks only**, A2 vs A1, paired per check.
> - Test: **McNemar's exact test** on the paired per-check outcomes (each check is graded under
>   both arms on the same data — the paired design is far more powerful than comparing two
>   independent proportions, and is the only test with adequate power at n≈20).
> - Pre-registered falsification: **H1 is rejected if the A2−A1 discordant-pair split is not
>   significant at p<0.05, or if the point estimate of the improvement is below +15pp.**
> - Secondary endpoints, each reported with its own CI: overall correct-rate, wrong-but-ran rate,
>   abstention rate (see I2), grain-tagged rate on paraphrased wordings (see I9).
> - Every arm-comparison figure in the report carries a CI. A bare bar chart of six percentages
>   is not an acceptable output of this experiment.

### B5. The bank tests whether a correct view *exists*, not whether the model *chooses* it. A2 currently cannot fail. (Direct answer to §6 open question 2.)

**Issue.** Yes — the concern in §6.2 is real, and it is sharper than the draft frames it. Take
the views A2 actually generates on `ecommerce/` from the three confident edges: an order-grain
rollup of `order_items`, a product-grain rollup of `order_items`, and a customer-grain rollup of
`orders`. Now walk the ecommerce questions:

- **E2, E3, E4, E7** — answerable as `SELECT AVG(<col>) FROM order_items_by_order`, optionally
  joined to `orders` for a status filter. One view is name-plausible; the question literally says
  "per order" / "order value". This is **lexical matching from the question's noun to the view's
  name**, not grain reasoning.
- **E9** ("top 5 products by units sold") — `SELECT ... FROM order_items_by_product ORDER BY
  total_quantity DESC LIMIT 5`. Same lexical match.
- **E6, E8** — require a two-hop path or a filter that the pre-aggregated view has already
  destroyed. No view is correct; the model must fall back to raw tables.

So the current bank has **zero questions where two or more views are plausible and only one is
right**. There is no question where the lexically-obvious view is the *wrong* one. A2 is
therefore unfalsifiable in the direction that matters: it can be beaten by a model that does
nothing but match the question's head noun against view names, and it can never be penalised for
using a view reflexively.

Related: E8 is currently the only place A2 can hurt (the product-grain view pre-aggregates across
all statuses, so using it for "completed orders only" is silently wrong) — and it is tagged
`G+F`, not flagged as a view-misuse trap, so that signal will be invisible in the analysis.

**Failure scenario.** A2 posts +25pp, the report headlines "generated grain layer rescues 4B
models", and the mechanism is actually "we handed the model a pre-computed answer under a name
that matches the question's noun." The claim does not survive the first real dataset where the
question's vocabulary and the view's name diverge — which is every real dataset.

**Proposed fix — two edits.**

*(a) §2, ecommerce block — add a `V` (view-selection) trap tag and six questions where the
lexically-obvious view is wrong.*

| # | Category | Trap | Question |
|---|---|---|---|
| E11 | analytical | V | What is the average price of a single line item across completed orders? (line grain is correct; the order-grain view is the trap) |
| E12 | analytical | V | Which product category generated the most revenue overall, across every order status? (product-grain view **is** correct here — the discriminating twin of E8, where it is wrong) |
| E13 | analytical | V+G | What is the average total spend per customer, counting only completed orders? (two-hop; the customer-grain view counts orders, not money — it is a decoy) |
| E14 | analytical | V+M | What is the average order value? — graded against `quantity_x_unit_price`, with `sum_unit_price` present in the same view as the wrong-measure distractor (see B2) |
| E15 | analytical | V | How many distinct customers placed at least one order in 2024? (no view helps; raw `orders` is correct) |
| E16 | analytical | G | On average, how much revenue does a customer generate? — **the gold must pre-register the denominator** (all 400 customers, including those with zero orders) and the check passes only if the model states that assumption in the existing `assumptions` field |

Add to the legend: **V** = view-selection trap (a generated view is name-plausible but wrong),
**M** = measure-selection trap.

*(b) §5, scoring — add mechanism instrumentation.* This is the part that turns an accuracy delta
into evidence about a mechanism:

> Every emitted SQL string is tagged by regex against the names of that dataset's generated
> views, producing a `viewUsage` field: `none` / `correct-view` / `wrong-view` / `mixed`. The
> report cross-tabulates outcome bucket × viewUsage per arm. An A2 win that shows up mostly as
> `none` is **not** a view effect and must not be reported as one; a `wrong-view` rate that rises
> from A1 to A2 is a cost of the mechanism and is reported alongside the gain.

Without (b), A2's result is a black box and the §6.2 worry is unanswerable after the fact.

## IMPORTANT

### I1. All grain evidence comes from one schema, and one trap shape. Add a chasm-join dataset — the repo already has the files.

**Issue.** After B1, the `G` traps are entirely `ecommerce/`, and they are all the *same* shape:
a single one-to-many fan-out from a fact table to a parent. The design's §1 claim is about a
general mechanism. One trap shape on one schema cannot support it, and this is the honest answer
to §6.1: **the bank does overfit** — not to five schemas, to one schema and one trap family.

**Failure scenario.** The report claims the layer "rescues small models from grain errors." The
first reader who tries it on a chasm join (two independent fan-outs from one dimension) or a
temporal rollup finds it doesn't help, because neither was ever tested. The claim was never
scoped to what was measured.

**Proposed fix (§2 — add a sixth dataset block, no new data required).** Register
`ecommerce/products.csv` + `ecommerce/order_items.csv` + `public/samples/product_reviews.csv`
together as the **chasm** dataset. Verified: `product_reviews.ProductId` normalises to
`product_id` so `nameAgrees` fires, and every referenced ProductId is < 150, so containment is
1.0 and the edge is `confident`. Both `order_items` and `product_reviews` fan out from
`products` — the textbook chasm trap, and precisely the case RESEARCH.md's Honeydew source
covers.

| # | Category | Trap | Question |
|---|---|---|---|
| C1 | profiling | - | How many products, line items and reviews are there? (3 checks) |
| C2 | analytical | X | For each product category, what is the total revenue and the average review rating? (a naive three-way join multiplies revenue by review count and rating count by line-item count — both silently wrong) |
| C3 | analytical | X | Which product category has the best average rating per dollar of revenue? |
| C4 | analytical | X+F | Among products with at least 5 reviews, which has the highest total revenue? |

Add **X** = chasm / multi-fanout double-count to the legend. This is the strongest single
addition available at zero data cost: A2's per-edge rollup views are *exactly* the right fix for
a chasm (aggregate each fan-out separately, then join), so it is a genuine second test of the
mechanism rather than a repeat of the first.

Also add to §2 the temporal-grain trap on `stock_prices.csv` — currently four questions, all
untrapped: **S5 (TG): "What is the average total monthly trading volume?"** Naive `AVG(Volume)`
is off by roughly the number of trading days per month (~21x), so the trap is unmissable in the
data and free to add.

### I2. The three-bucket scheme rewards abstention, and A4 has the most machinery to trigger it.

**Issue.** §5 says converting wrong-but-ran into failed-to-run "is a partial win." But
`MODEL_PROPOSAL_JSON_SCHEMA` in the reused `ollama.ts` has an `unsupported` branch — a
first-class refusal the model can emit at any time. Under §5's bucketing, a refusal lands in
bucket 3 (failed-to-run, "safe") and is indistinguishable from a DuckDB error. Adding a required
`plan` object (A4) raises the structured-output burden on a 4B model, which is a well-known
driver of both refusals and schema-validation failures.

**Failure scenario.** A4/A5's `unsupported` rate triples. Correct-rate is flat, wrong-but-ran
drops sharply, and §5's rule declares a "partial win". The report claims forced planning makes
small models safer, when the model simply learned to give up more often under a heavier output
contract. The metric is gameable by any change that reduces attempt rate, and the design has no
guard against it.

**Proposed fix (§5).** Split bucket 3 and add a floor rule:

> Bucket 3 splits into **3a. Abstained** (model emitted `status: "unsupported"`), **3b. Malformed**
> (structured output failed Zod validation), **3c. Execution error** (DuckDB rejected the SQL or
> the guard blocked it). All three are reported separately per arm.
>
> **Floor rule:** a "safety win" (bucket 2 → bucket 3) may only be claimed if the arm's
> **correct-rate does not fall** relative to the comparison arm, and if the shift is into 3c, not
> 3a. A method that only raises abstention is reported as a capability regression, not a partial
> win.

### I3. Excluding execution repair leaves a binding-error confound that inflates A1 and A2. (Direct answer to §6 open question 5.)

**Issue.** Excluding execution-guided *self-correction as a ladder arm* is defensible and
correctly reasoned — RESEARCH.md §3 is right that it cannot touch a query that runs and returns
a wrong number. That is not the problem. The problem is what its absence does to the *baseline*.

RESEARCH.md §1 says schema linking buys 6.9–46.9pp, and RESEARCH.md §3 says a large share of
small-model failures are "no such column" / "no such table" binding errors. A1 and A2 inject
column names, types, sample values and view DDL. So a large part of the A1/A2 gain over A0 will
be **binding-error rescue** — bucket 3c shrinking — which is precisely the mechanism the design
says it is *not* testing. With no repair pass, A0's floor is artificially depressed by errors
that a single retry would fix, and the A2−A0 delta is inflated by an effect the report will
attribute to grain.

**Failure scenario.** A2−A0 = +30pp. The report attributes it to the grain layer. In truth +22pp
is "the model now knows the column is called `unit_price`, not `price`" and +8pp is grain. The
headline claim is wrong in magnitude and in mechanism, and a critic reproduces it in ten minutes
by adding a retry loop to A0 and watching the gap collapse.

**Proposed fix (§3, "Not on the ladder" paragraph — rewrite, and §5).**

> Execution-guided self-correction is not an *arm*, per RESEARCH.md §3: it addresses syntax and
> binding errors, and the grain trap produces a syntactically valid, successfully-executing,
> silently wrong query with no error to observe.
>
> It is, however, applied **uniformly to every arm** as a single one-shot repair on a DuckDB
> error (reusing exp17's repair path), so that failed-to-run rates are comparable across arms and
> the residual delta between arms is semantic rather than a binding-error artifact. Repair usage
> is logged per call (`repairUsed` / `repairSucceeded`) and reported per arm; the primary endpoint
> is computed on post-repair outcomes, with pre-repair outcomes reported as a secondary series.

Add to §5: *"The report states, per arm, the split of bucket-3 failures into binding errors
versus other errors, so a reader can see how much of any arm's gain is binding rescue rather than
grain correction."*

### I4. Ollama silently truncates over-long prompts **from the front**, which is where the DDL and profile live.

**Issue.** §4 freezes controls but never bounds prompt length. Verified: Ollama does not error
when a prompt exceeds `num_ctx` — it trims to fit and logs
`level=WARN msg="truncating input prompt" limit=... prompt=... keep=4 new=...`, and the trimmed
part is the *front* of the prompt. The reused `ollama.ts` sets `num_ctx` from `CHAT_NUM_CTX`
(default 16384), and A4/A5 stack profile + view DDL + few-shot + plan schema across five to six
datasets.

**Failure scenario.** On the widest dataset, A5's prompt exceeds `num_ctx`. The schema DDL and
the grain statements — the top of the prompt — are silently deleted. A5 scores *below* A2. The
report concludes "stacking mechanisms hurts small models; there is an interference effect." The
actual cause is a truncation warning in a log nobody read. This is a plausible way to invert the
whole ladder's shape.

**Proposed fix (§4, add two bullets).**

> - `num_ctx` is pinned to the same value on both machines and recorded in the manifest; it is
>   never allowed to differ by machine for memory reasons, since that would change truncation
>   behaviour between the 4B and 14B runs.
> - `prompt_eval_count` is asserted after every call: a call whose prompt token count exceeds
>   `0.8 × num_ctx` **fails the run** rather than being scored. Ollama truncates over-long
>   prompts silently and from the front — the DDL and grain statements are the first thing lost —
>   so an unchecked overflow is indistinguishable from "the mechanism did not work."

### I5. The coder-vs-general pair is generation-confounded. It cannot answer the question it is there to answer. (Direct answer to §6 open question 3.)

**Issue.** §4 pairs `qwen3:8b` against `qwen2.5-coder:7b`. These differ in *three* ways: code
tuning, base model generation (Qwen3 vs Qwen2.5), and parameter count (8B vs 7B). Any observed
difference is unattributable. The arm coverage (A0/A5 only) is a secondary concern; the model
choice is the primary defect.

**Failure scenario.** `qwen2.5-coder:7b` underperforms by 12pp. The report says "code tuning
degrades semantic reasoning" — a spicy, quotable, and unsupported claim, when the likelier
explanation is that Qwen2.5 is a generation behind Qwen3. Nobody can tell which from the data.

**Proposed fix (§4, model axis — replace the coder pair bullet).**

> - Coder-vs-general: a **same-base, same-size, same-quantisation** pair —
>   `qwen2.5:7b-instruct` (4.7GB) vs `qwen2.5-coder:7b-instruct` (4.7GB), both Q4_K_M, both
>   Qwen2.5. Code tuning is then the only variable. Arms A0 and A4(full stack) only, M4.
>   Optionally repeat at the target tier with `qwen2.5:3b-instruct` vs `qwen2.5-coder:3b-instruct`
>   on the 8GB machine, since the product claim is about the 4B tier, not 7B.
>
> **Pre-registered claim scope for this arm:** with two arms and one (or two) model pairs, this
> arm supports only a *directional, family-and-size-scoped observation* reported with its CI —
> e.g. "on this bank, at 7B within Qwen2.5, code tuning changed grain-trap accuracy by X pp
> (95% CI …)". The report must not generalise to "coder models are worse at semantic errors."

Both tags verified present on the Ollama registry at the same 4.7GB Q4 size.

### I6. The 14B control runs A0 only, so the headline comparison cannot distinguish "the method helps small models" from "the method helps everyone".

**Issue.** §1's claim is `4B + method ≥ 14B baseline`, and §4 runs `qwen3:14b` on A0 only. That
compares a fully-equipped 4B against an unequipped 14B — a valid but weak claim, and one that
cannot answer the obvious follow-up.

**Failure scenario.** The result lands, and the first question asked is "what does 14B + method
do?" If the method's benefit is *larger* at small scale, that is the genuinely interesting
finding and it is unmeasurable as designed. If 14B+A0 already beats 4B+A4, the headline dies and
there is no fallback analysis.

**Proposed fix (§4, model axis).** Change the `qwen3:14b` entry from "**A0 only**" to
"**A0 and A4 (full stack) only** — two arms, so the report can state whether the method's effect
size is larger at 4B than at 14B (the scale-interaction claim), not merely that a dressed-up 4B
reaches an undressed 14B." Cost: one extra arm × ~40 checks on the M4, trivially affordable
against the budget freed by B3 and B4(b).

### I7. No negative control on the profile. A1's gain may be a token-count effect. (Direct answer to §6 open question 4.)

**Issue.** §6.4 asks whether token count should be logged. Logging is necessary but not
sufficient — it shows a correlation exists, not which way causation runs. Prompt length grows
monotonically across the ladder, so "more information helps" and "more tokens help" are perfectly
collinear by construction and no amount of post-hoc logging separates them.

**Failure scenario.** A1 posts +12pp. The report claims the deterministic profile is
"disproportionately load-bearing at small scale", echoing RESEARCH.md §1. The real cause is that
a longer, more structured prompt shifts the model's output distribution toward careful SQL,
regardless of content. Unfalsifiable as designed.

**Proposed fix.** Adopt A1✗ (corrupted-profile arm) from B3 — it holds token count essentially
constant and varies only correctness of the content, which is the clean test. Plus, in §4:

> - Prompt and completion token counts are logged per call and reported per arm alongside
>   accuracy, so any token-count correlation is visible. Token count alone is not evidence of
>   mechanism; the A1✗ corrupted-profile control is what separates "the model read the profile"
>   from "the prompt got longer."

### I8. Question wording leaks the answer's grain. The bank may be measuring lexical pattern-matching.

**Issue.** E3 "average **order** value", E7 "average number of items **per order**", E2 "how many
line items does an **order** have". Every grain-trapped question names its correct grain in the
question text. A model with no grain understanding that maps "per X" → `GROUP BY X` /
"X value" → the X-grain view scores well.

**Failure scenario.** The method posts a large win, and it evaporates on the first real user
question phrased naturally ("how much do people usually spend with us?"), because the effect was
lexical. The experiment's external validity is zero and nothing in the design would reveal it.

**Proposed fix (§2, add a paragraph after the tables).**

> Every `G`, `V` and `TG`-tagged question is committed in **two wordings**: the explicit one
> shown above, and a paraphrase that never names the correct grain — e.g. E3 → "When someone
> places an order here, how much do they typically spend on it?"; E7 → "How many things does a
> typical purchase contain?"; W3 → "How strong does the wind usually get at its worst in a given
> month?". Both wordings share one gold value and are graded as separate checks. The report
> presents grain-trap accuracy **split by wording**. If an arm's advantage exists only on the
> explicit wording, the mechanism is lexical and the report must say so.

This roughly doubles the trap-check count, which is also the cheapest route to B4's n≥20.

### I9. Every dataset is pristine synthetic data. The inference step is being tested on the friendliest possible input.

**Issue.** All five CSVs are generated fixtures: no orphan foreign keys, no null join keys, no
duplicate primary keys, uniform value distributions, and `order_items.unit_price` exactly equals
`products.unit_price` for every row. `relationshipInference.ts`'s thresholds
(`CONTAINMENT_SOLID = 0.95`, `KEY_UNIQUENESS_MIN = 0.98`) will be met with perfect margins on
every edge.

**Failure scenario.** The claim "a deterministically inferred grain layer rescues small models"
ships, someone applies it to a real export with 3% orphan rows, the containment drops to 0.97,
the edge stays `confident` but the rollup view silently drops the orphans, and the answers are
wrong in a way nothing in the pipeline flags. The experiment never tested the inference step at
all — it tested a hand-perfect input to it.

**Proposed fix (§2, add a sixth dataset — deterministic mutation, ~30 lines of script).**

> `ecommerce-dirty/` — `ecommerce/` transformed by a committed, seeded mutation script:
> 3% of `order_items` rows re-pointed to a non-existent `order_id`; 1% of `orders.customer_id`
> set to NULL; 20 `orders` rows given no line items at all; one `products.product_id` duplicated.
> The **same** E-series questions are asked, with gold recomputed against the mutated data.
> Reported as a separate series: how much of the method's benefit survives imperfect keys. The
> gold for each affected question pre-registers the orphan convention (orphan line items are
> excluded from order-grain aggregates; orders with no items count as value 0, not as missing).

This is the single change that lets the conclusion generalise past "exactly these five CSVs",
and it is cheap because the questions and harness are already built.

### I10. Gold-answer provenance has no independent check.

**Issue.** §2 says gold is "hand-written SQL ... reviewed by a human-equivalent pass". On the
grain questions, the entire experiment turns on whether the gold SQL itself picked the right
grain. If the same author (or model) that wrote the questions wrote the gold, a systematic grain
misreading propagates silently into the fixture and every arm is graded against a wrong answer.
"Human-equivalent pass" is not a control; it is a description of the same process.

**Failure scenario.** E3's gold is computed as `AVG(quantity * unit_price)` over `order_items`
(line grain) rather than over order totals. A0 — which makes exactly that mistake — scores 100%,
A2 scores 0%, and the experiment reports that the grain layer *hurts*. Undetectable without a
second implementation.

**Proposed fix (§2, replace the gold-provenance sentence).**

> Every gold answer is computed by **two independently written SQL formulations** that must agree
> numerically before the fixture is committed — for grain-tagged checks, one written as an
> explicit two-step rollup (CTE aggregating to the target grain, then the outer aggregate) and
> one written in a structurally different way (window function, or `DISTINCT`-based
> de-duplication). Both formulations are committed in `fixtures/gold.json` alongside the value.
> A disagreement between the two is a design bug in the question, not a rounding issue, and the
> question is rewritten or dropped. No LLM-as-judge for numerics.

## MINOR

### M1. The question and check arithmetic in §2 is wrong.

§2 asserts "10+7+4+4+10 = 35 individual gold checks across 33 questions". Counting the tables as
written: titanic 7 questions, weather 7, stock 4, reviews 4, ecommerce 10 = **32 questions**; with
the two stated splits (one titanic question, S1) that is **34 checks**, and the titanic term is
10 where the table supports 8. The stock term is 4 where S1's split makes it 5.

*Failure scenario:* the denominators in the report are wrong by 1–3 and the "each check ≈2.9
points" claim is off. Small, but it means nobody has counted the bank.

*Fix (§2):* delete the hand-computed arithmetic sentence. Replace with: *"The bank is committed
as `fixtures/questions.json`; the question and check counts in this document are generated from
that file by the harness, never asserted by hand. A build-order test asserts the counts match."*

### M2. T6's null trap is not a trap.

T6 asks for "average Age of survivors, accounting for nulls correctly (not treating missing Age
as 0)". DuckDB's `AVG` ignores NULLs by default, so the naive query is already right — falling
into this trap requires the model to actively write `COALESCE(Age, 0)`, which it has no reason to
do. Verified: 48 of 891 rows have an empty Age field (5.4%).

*Fix (§2, titanic block):* retag T6 as `-` (floor), or replace with a real null trap where the
naive query is wrong: **"What fraction of all passengers were under 18?"** — the correct
denominator is all 891 passengers, but `COUNT(*) FILTER (WHERE Age < 18) / COUNT(Age)` silently
uses 843. That is a genuine silent-wrong-number null trap on this data.

### M3. The tolerance rule is self-contradictory and conflicts with the reused comparator.

§2 says "floats compared to 2 decimal places (0.01 relative or absolute, whichever is looser,
capped at 1% relative for large sums)" — three mutually inconsistent rules in one sentence
("2 decimal places" ≠ "0.01 relative" ≠ "1% relative"). The reused `score.ts` `normalizeValue`
does `Math.round(value * 100) / 100` and then requires **exact** equality, which is none of the
three.

*Fix (§2):* state one rule. Suggested: *"Scalar numerics match if `|actual − gold| ≤ max(0.01,
0.001 × |gold|)` (absolute 0.01 or 0.1% relative, whichever is larger). Counts and IDs must match
exactly. `score.ts`'s `normalizeValue` is extended with this tolerance rather than reused as-is —
its current round-to-2dp-then-exact-equality is stricter than intended and will fail correct
answers that differ in float summation order."* A 1% band on a ~$1M revenue sum is ±$10,000 and
too loose to be a correctness check.

### M4. Argmax and top-N questions are unstable if the gold has ties.

R3 ("highest average rating among products with ≥5 reviews") ranges over integer ratings 1–5 with
~3.5 reviews per product across 520 reviews and ~150 products — ties at 5.0 are likely. E9's
"top 5 products by units sold" sums integer quantities, so a tie at the rank-5/6 boundary is
plausible. exp17's `compareResult` with `topRowOnly` grades on a substring match of the gold
leader in the answer text, which under a tie is arbitrary.

*Fix (§2):* add — *"Every argmax / top-N question is verified tie-free against the data before
the fixture is frozen; if the gold has a tie at the reported boundary, the threshold is adjusted
(e.g. ≥8 reviews instead of ≥5) or the question is dropped. Ranked answers are graded on the full
ordered set, not the top row, so a tie cannot be graded arbitrarily."*

### M5. Titanic is the most memorised tabular dataset in existence, and this copy is synthetic.

The file has 48 null Ages (5.4%); the canonical Kaggle Titanic has 177 (19.9%), and the names
here are generated. A model answering partly from memory ("survival rate was 38%") produces a
plausible-looking wrong number on this data.

*Fix (§2, titanic caption):* note it explicitly — *"This is a synthetic Titanic-shaped file, not
the canonical Kaggle copy (891 rows but different values; 48 null Ages, not 177). Any answer that
matches the canonical dataset's statistics rather than this file's is scored wrong and flagged in
the report as suspected memorisation."*

### M6. `stock_prices.csv`'s role is undeclared.

Four questions, all untrapped, five checks (14% of the bank) with no bearing on the hypothesis.
That is fine — but only if its job is named.

*Fix (§2, stock caption):* *"Single-entity, trap-light — this dataset's job is the **regression
guard**: does piling on profile, views, few-shot and forced planning degrade accuracy on
questions that were never hard? An arm that wins on ecommerce and loses here is reported as a
tradeoff, not a win."* Then add to §5: *"Report per-arm accuracy on trap-free checks separately
from trapped checks; a drop on trap-free checks is a first-class finding."*

### M7. No viability budget. A method that wins accuracy but takes 90s per question is not a rescue.

§4 logs elapsed time and peak memory but §5 never uses them. The product context is a 4B model on
an 8GB Mac.

*Fix (§5):* *"Pre-registered viability budget: p95 end-to-end latency per question on the 8GB
machine must be under 30s and peak RSS under 6GB for a method to be reported as viable. An arm
that wins on accuracy but exceeds the budget is reported as 'accurate but not shippable at this
tier', with its latency and memory stated in the headline table, not a footnote."*

### M8. `qwen3.5:4b` is 3.4GB, not the ~2.5GB RESEARCH.md estimated.

Verified on the Ollama registry: `qwen3.5:4b` is 3.4GB Q4_K_M, 4.66B parameters, 256K context
window. Still 8GB-viable, but the margin against macOS plus a browser is thinner than RESEARCH.md
assumed, and the 256K default context makes an accidentally-large `num_ctx` far more expensive in
KV cache than `qwen3:4b`'s.

*Fix (§4):* *"`num_ctx` is pinned explicitly for every model — never left to the model's default —
and the pinned value is recorded in the manifest. `qwen3.5:4b` is 3.4GB with a 256K native
context; leaving `num_ctx` unpinned there will exhaust an 8GB machine."*

### M9. Multi-row checks are all-or-nothing; say so.

T5 (survival rate by Pclass × Sex, 6 rows), E9 (top 5), E10 (4 status rows) and W4 (12 months) are
graded by `compareResult`'s full-set signature comparison — one wrong cell fails the whole check.
That is defensible and constant across arms, so it does not confound the comparison, but it makes
the absolute accuracy level much lower than a reader will expect.

*Fix (§5):* *"Grading granularity is stated per question in the fixture (`scalar` / `row-set` /
`ranked`). Row-set checks are all-or-nothing. The report presents scalar and row-set accuracy
separately, because a bank-wide percentage mixes two very different difficulty regimes."*

## Over-engineering / budget

One flag in the other direction, since gold-plating is a defect here too.

**N=5 repeats is the most expensive thing in the design and buys the least.** At temperature 0
with a pinned digest, repeats measure backend nondeterminism, not variance of interest. The
current matrix is roughly 34 checks × 6 arms × 5 repeats × 4 models ≈ 4,000 model calls; exp17's
smaller matrix measured at 7–10 hours. B4(b)'s determinism probe plus N=2 cuts that by ~60%,
which more than pays for everything this review adds (B1's rewritten weather block, I1's chasm
dataset and S5, B5's six view-selection questions, I8's paraphrases, I9's dirty variant, B3's two
diagnostic arms scoped to ecommerce only, I6's second 14B arm). **Net effect on runtime should be
neutral to slightly negative — the fixes buy statistical power and falsifiability with budget
freed from repeats that measure nothing.**

Conversely, resist any temptation to add: an LLM-as-judge fallback, a retrieval index for the
few-shot arm, or a second FK-inference implementation. None of those is on the critical path to
the claim.

## Summary of the six questions asked in §6

1. **Is 33 questions / 5 datasets enough?** No — but not for the reason asked. The problem is not
   breadth of datasets, it is that after B1 all 7 grain-tagged checks come from one schema and one
   trap shape (single fan-out). Fix: chasm dataset (I1), temporal-grain questions (B1, I1),
   view-selection questions (B5), paraphrases (I8) → ≥20 trap checks across ≥4 schemas and 4 trap
   families (fan-out, chasm, temporal, view-selection).
2. **Is A2's win trivial by construction?** As written, **yes**. Every trapped ecommerce question
   maps to exactly one name-plausible view via the question's head noun; no question has two
   plausible views with one right; no question penalises reflexive view use. And separately, the
   view generator as specified cannot even compute order value (B2). Fix: B2's dual-measure rule +
   B5's six view-selection questions + `viewUsage` instrumentation.
3. **Can the ladder attribute a win to a mechanism?** Not currently — A5 duplicates A4 (B3), the
   ladder is purely cumulative so every result is order-dependent, and prompt length is perfectly
   collinear with the mechanism (I7). Fix: drop the duplicate, add A2′ and A1✗ on ecommerce only,
   log tokens, assert against `num_ctx` (I4).
4. **Is the coder-vs-general arm sufficient?** The arm coverage is the lesser issue; the model pair
   is generation-confounded and cannot answer the question at all (I5). Fix: same-base pair, plus
   a pre-registered claim-scope sentence.
5. **Is excluding execution-guided retry defensible?** As an *arm*, yes — RESEARCH.md's reasoning
   is correct and should be quoted in the report. But its absence from the *baseline* leaves a
   binding-error confound that inflates A1/A2 (I3). Fix: apply one-shot repair uniformly to all
   arms and report binding-error rates per arm. That turns the exclusion from a possible
   deck-stack into a defensible, documented choice.
6. **Other falsifiability holes.** No pre-registered effect size or test (B4), no negative control
   on the profile (I7), gold with no independent verification (I10), grain named in every question
   (I8), pristine synthetic keys (I9), abstention-gameable scoring (I2), and silent prompt
   truncation that could invert the ladder (I4).
